Docker Certified Associate (DCA) Domain 2.0: Image Creation, Management, and Registry — Explained

Domain 2.0 is about the artifacts of Docker: how images are built from Dockerfiles, how layers make them efficient, and how registries store and distribute them. The image is the unit of Docker — understand it deeply.

Exam weight: 20% · Free study preview from ByteBar

Dockerfiles: recipes for images

  • What a Dockerfile is — a text recipe: start FROM a base image, RUN commands to install things, COPY in your code, declare the CMD/ENTRYPOINT that runs at container start.
  • Layer caching — each instruction creates a cached layer. Rebuilds reuse unchanged layers — so order matters: put slow-changing steps (dependency installs) before fast-changing ones (your code).
  • Multi-stage builds — build in one stage (compilers, SDKs), copy only the result into a slim final stage. Small, secure production images without build tools.
  • .dockerignore — excludes files from the build context (like .gitignore for builds): faster builds, no secrets accidentally baked in.

Layers, tags, and image anatomy

  • Images are layered and read-only — stacked filesystem layers, each the diff of one instruction. Containers add a thin writable layer on top; delete the container and its writes vanish.
  • Sharing — images sharing base layers store them once. Ten images FROM the same base = one copy of the base on disk.
  • Tags vs. digests — tags (:1.4) are movable labels; digests (@sha256:…) identify exact content. :latest is convenient and non-reproducible — pin versions that matter.
  • Image size discipline — slim bases, multi-stage builds, no build tools in production images. Smaller images pull faster, scan cleaner, and attack-surface less.
Dockerfile instruction → image layer. Container = image + thin writable layer. Layers are why Docker is fast: build once, share everywhere, change little.

Registries: where images live

  • What a registry does — stores images, serves pulls, controls access. Docker Hub is the public default; companies run private registries (Docker Trusted Registry / Harbor / cloud registries) for their own images.
  • Repositories vs. registries — a registry hosts many repositories (one per image name), each holding tagged versions. registry.example.com/team/app:2.0 = registry / repository / tag.
  • Push/pull flow — docker push uploads new layers; docker pull downloads missing ones. Only changed layers transfer — the rest is already local.
  • Signing and trust — content trust (Notary) signs images so consumers verify publisher identity and integrity. Pulling unsigned images from the internet is trusting strangers.
  • Pruning — unused images, containers, and build cache accumulate: docker system prune reclaims the disk. Registries need retention policies too.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. A Dockerfile installs dependencies (slow, rarely changes) and then copies application code (fast, changes constantly). Why does the order matter?

  1. A. A. It doesn't — Docker rebuilds everything every time
  2. B. B. Layer caching: unchanged early layers are reused, so putting stable steps first makes rebuilds fast
  3. C. C. COPY must always be the last instruction by law
  4. D. D. RUN instructions can't come before COPY
Show answer & reasoning

B. Docker caches each layer and reuses it when the instruction and its inputs haven't changed. Dependencies-first means code changes only rebuild the last layers — seconds instead of minutes. Reverse the order and every code tweak reinstalls all dependencies. Order is performance.

2. A team's builds include the full JDK and build tools, producing 1.2GB production images. What is the standard fix?

  1. A. A. Buy bigger registry storage
  2. B. B. Multi-stage builds — compile in a builder stage, copy only the artifact into a slim runtime image
  3. C. C. Compress the image with gzip manually
  4. D. D. Use :latest tags
Show answer & reasoning

B. Multi-stage builds separate build-time needs (JDK, compilers) from runtime needs (JRE + app): the final image carries only what runs. Smaller images pull faster, scan faster, and expose less attack surface. Storage (A) treats the symptom.

3. Two teams push different images that both start FROM the same base image. How much extra disk does the second image's base layers consume?

  1. A. A. A full second copy
  2. B. B. Nothing extra — identical layers are stored once and shared
  3. C. C. Half, due to compression
  4. D. D. It depends on the tag name
Show answer & reasoning

B. Layers are content-addressed: identical layer = identical hash = stored once, referenced twice. This sharing is why a host with 50 images isn't 50× the base size — and why standardizing base images pays off in disk, pull time, and scanning.

4. A developer accidentally committed AWS keys into a Dockerfile ENV line and pushed the image to a registry. What are the two failures?

  1. A. A. ENV is deprecated; keys belong in CMD
  2. B. B. Secrets baked into image layers are permanent and distributed — use build secrets / runtime injection instead
  3. C. C. Registries can't store ENV variables
  4. D. D. AWS keys don't work in containers
Show answer & reasoning

B. Image layers are forever: anyone who pulls the image (now or from any cache/mirror) gets the keys, and "deleting" the line later doesn't purge existing copies. Secrets must arrive at runtime (mounted secrets, env from orchestrator) — never baked into layers. Rotate the keys immediately.
