Docker Certified Associate (DCA) Domain 6.0: Storage and Volumes — Explained

Domain 6.0 is the smallest DCA domain and pure concept: where container data lives, what survives what, and which storage option fits which need. Short, sweet, and very testable.

Exam weight: 10% · Free study preview from ByteBar

The persistence problem

Containers are ephemeral by design: the writable layer exists only while the container does. Anything worth keeping must live outside the container's lifecycle:

  • Volumes — Docker-managed storage in /var/lib/docker/volumes. Created explicitly or anonymously, shared between containers, backed up and migrated by Docker tooling. The production answer.
  • Bind mounts — map any host path into the container. Maximum flexibility, zero portability: the container now depends on that host's filesystem layout.
  • tmpfs mounts — RAM-only storage, never touches disk. For sensitive temporary data (decrypted secrets in use) and high-speed scratch.
Ask "what happens when the container is deleted?" Volumes persist. Bind mounts persist (they're the host's files). tmpfs evaporates. The writable layer evaporates.

Volume lifecycle and sharing

  • Named vs. anonymous volumes — named volumes (db-data) are deliberate and reusable; anonymous volumes (random hex names) are usually accidents of Dockerfiles — they accumulate and confuse. Name your volumes.
  • Sharing — multiple containers mount the same volume: the classic sidecar pattern (app writes logs, shipper reads them). Concurrent writes from multiple containers need application-level coordination — Docker won't serialize for you.
  • Drivers — volume drivers extend storage beyond local disk: NFS, cloud block storage, Ceph. docker volume create --driver — the data can live anywhere the driver reaches.
  • Backup and migration — back up volumes (not containers): run a throwaway container mounting the volume and archive it, or use driver-level snapshots. The volume is the data.
  • Pruning — docker volume prune removes unused volumes. Anonymous volumes from dead containers are the usual disk-eaters — another reason to name volumes.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. A container writes processed files to its writable layer. The container is removed during an upgrade. What happens to the files?

  1. A. A. They persist in the image
  2. B. B. They are lost — the writable layer dies with the container
  3. C. C. They move to a volume automatically
  4. D. D. They are backed up by the daemon
Show answer & reasoning

B. The writable layer's lifetime is the container's. Nothing migrates it, nothing backs it up — it simply ceases to exist. Data that matters must be written to a volume (or bind mount) from the start. "Written inside the container, container deleted" → gone.

2. Two containers need to share a set of TLS certificates, read-only, without baking them into images. What is the cleanest approach?

  1. A. A. COPY the certs into each image
  2. B. B. A named volume (or bind mount) with the certs, mounted read-only into both containers
  3. C. C. Pass the certs as ENV variables
  4. D. D. Use tmpfs so they never touch disk
Show answer & reasoning

B. Shared read-only storage decouples the certs from the images: rotate the files once, both containers see the update, no rebuilds. Baking into images (A) means rebuilding to rotate; ENV (C) exposes secrets in inspectable config; tmpfs (D) evaporates on restart.

3. An admin runs `docker volume prune` on a host with many stopped containers that used anonymous volumes. What happens?

  1. A. A. Nothing — prune only affects images
  2. B. B. Unused anonymous volumes are deleted, reclaiming their disk space
  3. C. C. Running containers lose their volumes
  4. D. D. Named volumes are deleted too
Show answer & reasoning

B. Prune removes unused volumes — anonymous volumes from long-dead containers are the classic reclaim. Running containers' volumes are in use and untouched (C); named-but-unused volumes are also removed, which is why the command asks for confirmation. Anonymous volumes: name them or lose track of them.

4. A container processes credit-card data in memory and must guarantee no trace touches the disk, even in swap or crash dumps. Which mount fits?

  1. A. A. A named volume with encryption
  2. B. B. tmpfs — RAM-only, never written to disk
  3. C. C. A bind mount to /tmp
  4. D. D. The writable layer
Show answer & reasoning

B. tmpfs lives purely in RAM: nothing is written to disk, so disk forensics finds nothing. (Disable swap or use encrypted swap for the full guarantee — tmpfs can be swapped.) Volumes (A) and bind mounts (C) are disk-backed by definition; the writable layer (D) is disk-backed too.
