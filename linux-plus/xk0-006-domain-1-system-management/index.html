CompTIA Linux+ (XK0-006) Domain 1.0: System Management — Explained

Domain 1.0 is the largest Linux+ domain: the fundamentals of keeping Linux systems running — how they boot, how the kernel talks to hardware, how storage is organized, how networking is configured, and how data is protected.

Exam weight: 23% · Free study preview from ByteBar

Boot process: from power to prompt

  • The sequence — firmware (UEFI/BIOS) → bootloader (GRUB2) → kernel loads → init (systemd, PID 1) → targets reached. Know the order: "won't boot" diagnosis starts by asking how far it got.
  • GRUB2 — the bootloader: picks the kernel, passes parameters, offers the boot menu. A broken GRUB config = a system that can't start its kernel — fixable from rescue media.
  • systemd targets — the modern "runlevels": multi-user.target (text/console), graphical.target (GUI). systemctl get-default/set-default controls the boot target.
  • Kernel modules — drivers loaded on demand: lsmod (what's loaded), modprobe (load/remove), /etc/modprobe.d/ (persistent config). Missing module = hardware the kernel can't see.

Storage: partitions, LVM, and filesystems

  • Partitioning — GPT (modern, UEFI, huge disks) vs. MBR/msdos (legacy, 2 TB limit). Partitions are carved with fdisk/gdisk/parted.
  • LVM — the flexible layer: physical volumes → volume groups → logical volumes. Resize filesystems without repartitioning; take snapshots for backups. "We need more space on /var" is an LVM afternoon, not a reinstall.
  • RAID — RAID 0 (striping: speed, no redundancy), RAID 1 (mirroring: redundancy), RAID 5 (striping + parity: one disk may fail), RAID 6 (two may fail), RAID 10 (mirror of stripes: performance + redundancy). RAID is uptime, not backup.
  • Filesystems — ext4 (the default workhorse), XFS (large files/high performance), Btrfs (snapshots, pooling). mount/umount, and /etc/fstab for persistence — a bad fstab entry can halt a boot, so keep a known-good backup.
GPT for modern, MBR for legacy. LVM = flexible volumes. RAID = survive disk failure (not backup). fstab = mounts that persist — and can break boots.

Networking, packages, and backups

  • Network configuration — interfaces (ip addr), routes (ip route), DNS (/etc/resolv.conf, systemd-resolved), hostnames. ip replaced ifconfig/route — know the modern commands.
  • Connectivity ladder — link (cable/interface up?) → address (correct IP/subnet?) → gateway (route?) → DNS (resolves?) → remote (port open? firewall?). Diagnose bottom-up, every time.
  • Package management — apt/dpkg (Debian/Ubuntu), dnf/rpm (RHEL/Fedora), zypper (SUSE). Repositories provide signed packages; update caches before installing; know which family a distro belongs to.
  • Backups — tar (archives), rsync (efficient syncs — the workhorse), dd (bit-for-bit — powerful and dangerous). The 3-2-1 rule: 3 copies, 2 media types, 1 offsite. An untested backup is a rumor.
  • Virtualization basics — hypervisors (KVM on Linux), VMs vs. containers (full OS vs. shared kernel). Know where your workload actually runs.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. A server needs more space on its /var logical volume without downtime or repartitioning. Which technology makes this possible, and roughly how?

  1. A. A. RAID 0 — stripe more disks
  2. B. B. LVM — extend the logical volume (and grow the filesystem) from free space in the volume group
  3. C. C. A bigger /etc/fstab
  4. D. D. Reinstall with larger partitions
Show answer & reasoning

B. LVM decouples filesystems from physical partitions: lvextend grows the logical volume from VG free space, then the filesystem grows into it — online, no repartitioning. That's LVM's core value proposition. RAID (A) is about disk redundancy, not flexible volumes.

2. A system stops during boot with errors about an unmountable filesystem listed in fstab. What likely happened, and what's the recovery path?

  1. A. A. The kernel is corrupted — reinstall
  2. B. B. A bad fstab entry (typo, removed disk) halts the boot — fix from rescue/emergency mode or a live environment
  3. C. C. GRUB is fine so nothing is wrong
  4. D. D. The CPU failed
Show answer & reasoning

B. systemd tries to mount everything in fstab at boot; a bad entry (wrong UUID, disk removed) blocks the boot. Recovery: emergency shell or live media, fix the entry, reboot. This is why you keep fstab backups and use nofail for non-critical mounts. The kernel (A) loaded fine — it got past GRUB.

3. A database needs to survive a single disk failure with good read performance and minimum 3 disks. Which RAID level, and what is its limitation?

  1. A. A. RAID 0
  2. B. B. RAID 5 — striping with parity survives one disk failure; limitation: rebuilds are slow and a second failure during rebuild is fatal
  3. C. C. RAID 1
  4. D. D. No RAID — backups are enough
Show answer & reasoning

B. RAID 5's parity survives exactly one failure with good capacity efficiency (minimum 3 disks). The honest limitation: on large modern disks, rebuilds take so long that a second failure during rebuild kills the array — which is why RAID 6 exists for big arrays. RAID is uptime; backups are recovery — you need both (D confuses the two).

4. A technician must copy only changed files from /data to a backup server efficiently over SSH, preserving permissions. Which tool and why?

  1. A. A. tar — simplest archive
  2. B. B. rsync — transfers only deltas, preserves permissions/ownership, works over SSH
  3. C. C. dd — bit-for-bit copy
  4. D. D. cp -r
Show answer & reasoning

B. rsync's delta-transfer sends only changed blocks (fast incremental backups), -a preserves permissions/ownership/timestamps, and it tunnels over SSH natively. tar (A) re-copies everything; dd (C) copies whole devices bit-for-bit (wrong granularity, dangerous); cp (D) has no delta or remote logic.
