Certified Kubernetes Administrator (CKA) Domain 3.0: Services & Networking — Explained

Domain 3.0 is how traffic moves in a cluster: the Service abstraction that survives pod churn, the DNS every pod uses, the Ingress front door, and the NetworkPolicies that decide who may talk to whom — plus what the admin must keep healthy underneath.

Exam weight: 20% · Free study preview from ByteBar

Services and kube-proxy

  • The Service abstraction — a stable virtual IP (ClusterIP) and DNS name selecting pods by label. Pods die and get replaced; the Service never changes. Endpoints track the current healthy pod IPs.
  • kube-proxy — the per-node agent that implements Services: programs iptables/IPVS rules so the virtual IP actually routes to backends. If Services stop working cluster-wide, kube-proxy health is on the suspect list.
  • Service types — ClusterIP (internal), NodePort (a port on every node), LoadBalancer (cloud LB integration), headless/None (DNS returns pod IPs directly — for StatefulSets).
  • CoreDNS — cluster DNS: Services resolve as svc.namespace.svc.cluster.local; pods get DNS automatically. DNS failures in a cluster are very often CoreDNS pods unhealthy or misconfigured — check them early.

Ingress: the HTTP front door

  • What Ingress does — L7 routing: one entry point, routing by host and path to backend Services, commonly terminating TLS. Many HTTP services, one public address.
  • IngressClass and controllers — the Ingress resource is just config; an ingress controller (nginx, Traefik, cloud LBs) must be running to act on it, selected via IngressClass. "I created the Ingress and nothing happens" → no controller is watching.
  • TLS — certificates live in Secrets referenced by the Ingress; termination happens at the controller, backend traffic is plain HTTP (or re-encrypted).
  • Admin angle — installing and keeping the controller healthy, choosing the right class per environment, and verifying backend Services actually have endpoints.
Service = stable L4 address for pods. Ingress = L7 HTTP routing in front of Services. Neither works without its implementer: kube-proxy for Services, a controller for Ingress.

NetworkPolicies and CNI

  • Default open — pods accept traffic from anywhere unless a NetworkPolicy selects them. Isolation is opt-in, not default — a common false assumption.
  • How policies work — select pods by label; declare allowed ingress/egress by pod selector, namespace selector, or IP block, with optional ports. Select-with-no-rules = deny that direction (default-deny pattern).
  • CNI plugins — the Container Network Interface is what implements pod networking: Calico, Cilium, Flannel, Weave. The CNI assigns pod IPs and (for policy-capable CNIs) enforces NetworkPolicies.
  • Admin troubleshooting — "policy applied but traffic still flows" → is the CNI policy-capable and healthy? "Pods can't reach each other at all" → CNI misconfiguration or a default-deny with no allow rules. Always verify the enforcement layer, not just the YAML.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. All Services in a cluster suddenly stop routing to pods, though the pods themselves are healthy. Which component should the admin investigate first?

  1. A. A. etcd
  2. B. B. kube-proxy — it programs the per-node rules implementing Services
  3. C. C. The scheduler
  4. D. D. CoreDNS
Show answer & reasoning

B. kube-proxy is the Service implementer: it writes the iptables/IPVS rules that make virtual IPs reach backends. Healthy pods + dead Services cluster-wide points at the programming layer, not the pods. The scheduler (C) places pods (they're already placed); etcd (A) stores state (reads still work).

2. Pods can't resolve Service names, but IP connectivity between pods works. What is the most likely culprit?

  1. A. A. The CNI plugin
  2. B. B. CoreDNS — the cluster DNS provider; name resolution fails while IPs still route
  3. C. C. kube-proxy
  4. D. D. The Ingress controller
Show answer & reasoning

B. "IPs work, names don't" isolates the failure to DNS — CoreDNS pods, its Service, or its configuration. The CNI (A) provides pod IPs (those work); kube-proxy (C) implements Service VIPs (IP-level). Name resolution has exactly one provider: check it first.

3. An Ingress resource was created correctly but no traffic is routed and no controller logs mention it. What is the likely cause?

  1. A. A. The backend pods are unhealthy
  2. B. B. No ingress controller is running/watching that IngressClass — the resource is config without an implementer
  3. C. C. The TLS secret is missing
  4. D. D. DNS is broken
Show answer & reasoning

B. Ingress resources do nothing alone — a controller must watch the IngressClass and act. No controller, no routing, no logs mentioning it. Backend health (A) would produce 503s through a working controller, not silence. Always verify the implementer exists.

4. A NetworkPolicy selecting all pods in a namespace was applied, but pods still receive traffic from anywhere. The YAML is valid. What should the admin check?

  1. A. A. The policy's labels
  2. B. B. Whether the CNI plugin enforces NetworkPolicies — a non-enforcing CNI makes policies documentation only
  3. C. C. kube-proxy
  4. D. D. The pod resource limits
Show answer & reasoning

B. NetworkPolicies are declared in YAML but enforced by the CNI: Calico and Cilium enforce; Flannel and kubenet don't. Valid YAML + zero effect = the enforcement layer doesn't implement policies. The admin checks the CNI's capabilities before debugging selectors (A).
