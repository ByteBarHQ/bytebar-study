Certified Kubernetes Administrator (CKA) Domain 2.0: Workloads & Scheduling — Explained

Domain 2.0 is about the work Kubernetes runs: how applications are packaged as pods, kept alive by controllers, placed by the scheduler, and scaled with demand. Understand the objects and their relationships and the domain clicks into place.

Exam weight: 15% · Free study preview from ByteBar

Pods: the smallest deployable unit

  • What a pod is — one or more containers sharing network (one IP) and storage, scheduled together on one node. The atom of Kubernetes scheduling: you never schedule a lone container.
  • Multi-container patterns — sidecar (helper alongside the main container: log shippers, proxies), init containers (run to completion before app containers start: setup, migrations).
  • Probes — liveness (is it alive? restart if not), readiness (is it ready for traffic? pull from service if not), startup (give slow starters time before liveness kicks in). Readiness ≠ liveness: a pod can be alive but not ready.
  • Labels and selectors — the glue: labels tag objects, selectors match them. Services find pods by selector, not by name — which is why pods can die and be replaced freely.

Controllers: keeping the desired state

  • Deployments — the standard way to run stateless apps: declare "3 replicas of this pod," and the deployment maintains it through failures and updates. Rolling updates replace pods gradually; rollbacks revert.
  • ReplicaSets — what deployments manage underneath: ensures N pod copies exist. You rarely touch one directly.
  • StatefulSets — for stateful apps (databases): stable network identities, ordered deployment/scaling, persistent storage per pod. When identity and order matter, StatefulSet.
  • DaemonSets — one pod per node (or per selected nodes): log collectors, monitoring agents, network plugins. "Every node gets one."
  • Jobs and CronJobs — run-to-completion work: a Job runs once; a CronJob runs on a schedule. Batch migrations, nightly reports.
Controller quick reference: Deployment = stateless apps; StatefulSet = databases; DaemonSet = per-node agents; Job = run once; CronJob = run on schedule.

Scheduling and resources

  • How scheduling works — the scheduler watches for unscheduled pods, filters nodes that can't run them (insufficient CPU/memory, taints), then scores the rest and picks the best. It doesn't run containers — the kubelet does.
  • Requests vs. limits — requests guarantee resources (scheduling decisions use them); limits cap usage (breach CPU limit → throttled; breach memory limit → OOM-killed). Requests ≤ limits, always.
  • Node affinity / taints and tolerations — affinity attracts pods to nodes ("run on SSD nodes"); taints repel pods unless they tolerate them ("no general workloads on GPU nodes").
  • Autoscaling — HPA (horizontal pod autoscaler) adds replicas on metrics like CPU; VPA adjusts requests/limits; cluster autoscaler adds nodes. Three different scalers for three different bottlenecks.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. A team runs a web API that must survive pod failures and update without downtime. Which controller fits, and why?

  1. A. A. Job — it runs the API to completion
  2. B. B. Deployment — maintains replicas and does rolling updates
  3. C. C. DaemonSet — one API pod per node
  4. D. D. A bare Pod — simplest possible
Show answer & reasoning

B. Deployments maintain the declared replica count through failures (self-healing) and roll out new versions gradually (rolling updates) with rollback available. Jobs (A) terminate; DaemonSets (C) are for node agents, not scaled APIs; bare pods (D) are never rescheduled when they die.

2. A pod is running but a dependent cache isn't ready, so the pod shouldn't receive traffic yet. Which probe controls this?

  1. A. A. Liveness — it will restart the pod
  2. B. B. Readiness — it controls whether the pod gets traffic
  3. C. C. Startup — it delays all other probes
  4. D. D. None — probes can't control traffic
Show answer & reasoning

B. Readiness gates traffic: failing readiness removes the pod from service endpoints without restarting it. Liveness (A) would restart a merely-unready pod — the classic misconfiguration that turns a slow dependency into a crash loop. Alive ≠ ready.

3. A pod specifies CPU request 500m and limit 1000m. What do these mean?

  1. A. A. It always uses exactly 750m
  2. B. B. The scheduler guarantees 500m; the pod is throttled if it tries to exceed 1000m
  3. C. C. It can use 1000m only on weekends
  4. D. D. Requests and limits must be equal
Show answer & reasoning

B. Requests are the scheduling guarantee (the scheduler only places the pod where 500m is free); limits are the enforcement ceiling (CPU throttling beyond 1000m; memory beyond limit → OOM kill). Requests drive placement; limits drive runtime enforcement.

4. Traffic to an API doubles every weekday morning. Which autoscaler adds more pod replicas based on CPU?

  1. A. A. Vertical Pod Autoscaler (VPA)
  2. B. B. Cluster autoscaler
  3. C. C. Horizontal Pod Autoscaler (HPA)
  4. D. D. CronJob
Show answer & reasoning

C. HPA scales replicas (horizontal) on metrics like CPU — more pods for more traffic. VPA (A) resizes requests/limits (vertical); the cluster autoscaler (B) adds nodes; CronJobs (D) run scheduled tasks. "More pods" → horizontal → HPA.
