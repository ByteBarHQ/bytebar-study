Certified Kubernetes Administrator (CKA) Domain 4.0: Storage — Explained

Domain 4.0 is the smallest CKA domain and the most conceptual: how Kubernetes gives mortal pods immortal storage. Learn the PV → PVC → StorageClass chain once and every storage question answers itself.

Exam weight: 10% · Free study preview from ByteBar

Why pods need help with storage

  • Containers are ephemeral — when a container dies, its writable layer dies with it. Restart the pod and your data is gone. Any data that must survive needs a volume.
  • Volume types — emptyDir (survives container restarts, dies with the pod — scratch space), hostPath (a node directory — ties the pod to that node, avoid in production), configMap/secret (inject configuration as files), and persistent volumes (real storage, outlives pods).
  • The pod spec references volumes — the pod declares "I need this volume mounted at this path." Storage details stay out of the pod where possible.

PVs, PVCs, and StorageClasses: the chain

  • PersistentVolume (PV) — a chunk of real storage provisioned by an admin (or dynamically), with capacity and access modes. Cluster-scoped: it exists independently of any pod.
  • PersistentVolumeClaim (PVC) — a pod's request for storage: "I need 10Gi, ReadWriteOnce." Namespace-scoped. Kubernetes binds a matching PV to the claim.
  • StorageClass — the template for dynamic provisioning: instead of pre-creating PVs, the StorageClass tells Kubernetes how to create one on demand when a PVC appears (which provisioner, which disk type).
  • The flow — pod needs storage → PVC requests it → StorageClass provisions (or an existing PV binds) → pod mounts the claim. Developers write PVCs; the platform handles PVs.
  • Reclaim policies — what happens to the PV when the PVC is deleted: Retain (keep the data, manual cleanup), Delete (destroy the volume), Recycle (legacy scrub-and-reuse).
PV = the actual storage (admin/platform). PVC = the request (developer). StorageClass = the recipe for making PVs on demand. Claim → bind → mount.

Access modes: who can mount how

  • ReadWriteOnce (RWO) — mounted read-write by one node. The common case for databases.
  • ReadOnlyMany (ROX) — mounted read-only by many nodes. Shared config, static assets.
  • ReadWriteMany (RWX) — mounted read-write by many nodes. Needs a filesystem that supports it (NFS, CephFS) — not every storage backend can.
  • Matching matters — a PVC requesting RWX only binds to a PV offering RWX. Mode mismatch = claim sits Pending forever.

Try it: 4 sample questions

Sample questions to check your understanding of this domain. Answers and full reasoning are tucked under each one.

1. A developer's pod needs 10Gi of storage that survives pod restarts and is created automatically when requested. Which objects are involved?

  1. A. A. A hostPath volume — simplest
  2. B. B. A PVC requesting 10Gi, fulfilled by dynamic provisioning via a StorageClass
  3. C. C. An emptyDir volume
  4. D. D. A ConfigMap
Show answer & reasoning

B. The developer writes a PVC (the request); a StorageClass dynamically provisions the PV — no admin pre-creation, survives pod death. hostPath (A) ties the pod to one node; emptyDir (C) dies with the pod; ConfigMaps (D) hold config, not 10Gi of data.

2. A database pod was deleted and recreated, but its data is gone. The pod used an emptyDir volume. What went wrong?

  1. A. A. emptyDir survives pod deletion — this is a scheduler bug
  2. B. B. emptyDir only survives container restarts; pod deletion wipes it — persistent data needs a PV/PVC
  3. C. C. The database should have used a ConfigMap
  4. D. D. Nothing — databases shouldn't store data
Show answer & reasoning

B. emptyDir's lifetime is the pod, not the container: it survives container crashes (useful scratch space) but dies with the pod. Durable data needs a PersistentVolumeClaim. This is the #1 storage misconception — always verify the volume type.

3. A shared media library must be mounted read-write by pods on many nodes simultaneously. Which access mode is required?

  1. A. A. ReadWriteOnce (RWO)
  2. B. B. ReadOnlyMany (ROX)
  3. C. C. ReadWriteMany (RWX)
  4. D. D. Access modes don't matter for shared data
Show answer & reasoning

C. Many nodes × read-write = ReadWriteMany. RWO (A) allows one node; ROX (B) is read-only. And the backend must actually support RWX (NFS/CephFS do; plain block storage doesn't) — a PVC asking for RWX on an RWO-only provisioner pends forever.

4. A PVC is deleted and the admin wants the underlying data preserved for manual review. Which reclaim policy should the PV use?

  1. A. A. Delete — removes the volume immediately
  2. B. B. Retain — keeps the PV and its data for manual handling
  3. C. C. Recycle — scrubs and reuses automatically
  4. D. D. Reclaim policies only apply to ConfigMaps
Show answer & reasoning

B. Retain keeps the PV and its data after the claim is gone — the admin then inspects, backs up, or manually cleans up. Delete (A) would destroy the very data to be reviewed. Retain is the safe default when data matters more than automation.
